# Архітектура Stream Translate

Оновлено: 2026-08-05

## 1. Що це

Chrome-розширення (MV3), яке накладає інтерактивні субтитри з AI-перекладом
(Gemini) на відеоплеєри, плюс Java-бекенд, що зберігає за користувачем словник
і налаштування.

Дві частини живуть в одному репозиторії, але деплояться окремо:

```
Stream-Translate/
├── src/          розширення (TypeScript, esbuild → dist/)
├── backend/      Spring Boot 4.1 + PostgreSQL
├── assets/       статика розширення (іконки, overlay.css)
├── docs/         документація
└── tests/        юніт-тести чистих функцій (Node, без залежностей)
```

## 2. Структура джерел розширення

Папки відповідають **контекстам виконання Chrome**, а не типам файлів — бо саме
межа контексту визначає, що модулю доступно (DOM? мережа? `chrome.identity`?).

```
src/
├── background/index.js   Service worker — ЄДИНА точка виходу в мережу
├── popup/                UI вкладок: профіль / слова / налаштування
│   ├── index.js
│   └── popup.html
├── content/              Працює на сторінці відеосервісу
│   ├── index.ts          оркестрація: init(), переприв'язка при перерендері
│   ├── state.ts          спільний стан content-script
│   ├── adapters/         платформо-специфічне (YouTube; далі Netflix)
│   │   ├── siteAdapter.ts     інтерфейс SiteAdapter
│   │   ├── siteAdapters.ts    реалізації
│   │   ├── activeAdapter.ts   вибір адаптера за host
│   │   └── ytBridge.js        MAIN world (доступ до movie_player)
│   ├── subtitles/        здобуття й показ реплік
│   │   ├── subtitleParser.ts  SRT/VTT/json3 → Cue[]   (чистий, тестований)
│   │   ├── youtubeCaptions.ts вибір треку, retry     (чистий, тестований)
│   │   ├── subtitles.ts       завантаження, стани
│   │   └── sync.ts            timeupdate → рендер репліки
│   └── overlay/          те, що бачить користувач поверх відео
│       ├── ui.ts, interaction.ts, translate.ts, settingsPanel.ts
├── api/                  клієнт нашого бекенду
│   ├── backendAuth.ts    ЖИВЕ У ВОРКЕРІ: токени, fetch, refresh, міграції
│   └── authClient.ts     тонкі sendMessage-обгортки для UI
└── shared/               спільне для всіх бандлів
    ├── messages.ts       контракт: імена повідомлень + ключі storage
    ├── constants.ts, i18n.ts, utils.ts, cacheKey.ts, chrome.d.ts
```

**Чому `api/backendAuth.ts` не в `background/`:** його імпортує лише воркер, але
логічно це клієнт зовнішньої системи, а не частина оркестрації воркера. Межа
«де виконується» задокументована коментарем у файлі.

## 3. Ключове архітектурне рішення: воркер — єдиний вихід у мережу

Ані content-script, ані popup не роблять `fetch` до бекенду чи Gemini. Усе йде
через `chrome.runtime.sendMessage` у service worker.

```
  content script            service worker              зовнішні системи
 ┌──────────────┐   msg    ┌────────────────┐   fetch   ┌──────────────┐
 │ tooltip      │ ───────► │ background/    │ ────────► │ Gemini API   │
 │ settingsPanel│ ◄─────── │  index.js      │ ────────► │ наш бекенд   │
 └──────────────┘  resp    │  api/backendAuth│          └──────────────┘
 ┌──────────────┐          └────────────────┘
 │ popup        │ ───────►        │
 └──────────────┘                 ▼
                          chrome.storage.local
```

Наслідки (усі — свідомі):
- **Токени ніколи не потрапляють у контекст сторінки.** YouTube-скрипти
  виконуються в тому ж процесі, що й content-script; тримати там JWT — ризик.
- **CORS не потрібен.** `fetch` із воркера до домену з `host_permissions` не
  підпадає під CORS, тому бекенду не треба CORS-конфігурації для розширення.
  (Знадобиться, коли з'явиться веб-дашборд — це вже справжня сторінка.)
- **`chrome.identity.launchWebAuthFlow` доступний лише в extension-контексті** —
  у content-script його просто немає.
- Ціна: кожен виклик — це раунд-тріп повідомленням, і воркер може «заснути».
  Для нашого профілю навантаження (дії користувача, не потік) це не проблема.

## 4. Живий синк без перезавантаження сторінки

**Шина подій — `chrome.storage.local`.** `chrome.storage.onChanged` розсилається
в **усі** контексти розширення автоматично. Це дає синхронізацію без
`chrome.tabs.sendMessage`, без знання про відкриті вкладки і без перезавантаження.

| Подія | Хто пише | Хто слухає | Що робить |
|---|---|---|---|
| Змінились налаштування | popup / панель | панель, popup | перечитує поля |
| Логін / логаут | воркер | панель, popup | перемальовує блок акаунта |
| Збережено/видалено слово | воркер (`wordsRevision++`) | popup | перечитує список і статистику |

`wordsRevision` — простий лічильник. Значення не має сенсу; важливий сам факт
зміни. Це дешевше й надійніше, ніж класти в storage весь список слів.

Переклад підхоплює нові налаштування автоматично: воркер читає `storage` на
**кожному** запиті, а не кешує в пам'яті.

## 5. Дані користувача: local-first

```
chrome.storage.local ──(логін)──► бекенд ──(логін на іншому пристрої)──► storage
```

- **Розлогінений:** слова йдуть у локальний `wordbook`, налаштування — у storage.
  Розширення повністю робоче офлайн.
- **На логіні:** налаштування тягнуться з акаунта у storage (ключ «сам
  вставляється»), а локальний `wordbook` **мігрує** на бекенд. `POST /words`
  ідемпотентний (upsert за `user+lemma+мови`), тож повтор безпечний. Локальний
  список чистимо лише коли перенеслось усе — краще спробувати ще раз наступного
  логіну, ніж втратити дані.
- **Залогінений:** слова йдуть одразу на бекенд; налаштування пишуться і
  локально (щоб переклад працював), і на акаунт (щоб синхронізувались).

## 6. Автентифікація

```
розширення                     Google                  наш бекенд
    │  launchWebAuthFlow          │                         │
    │ ──────────────────────────► │                         │
    │  ◄── id_token (фрагмент) ── │                         │
    │                                                       │
    │ ─── POST /auth/google { idToken } ──────────────────► │ перевірка через
    │ ◄── { accessToken (15 хв), refreshToken (30 д) } ───  │ Google JWKS
    │                                                       │
    │ ─── GET /words  Authorization: Bearer <access> ─────► │ наш HMAC-JWT
```

**Два різні ключі, які не можна плутати:**
- Google JWKS — перевіряє Google ID-токен. Використовується **лише** в
  `/auth/google` (`GoogleTokenVerifier`), не підключений до filter chain.
- Наш HMAC-секрет — підписує й перевіряє наші токени. Це єдиний `JwtDecoder`-бін
  у контексті, тому конфлікту бінів немає.

`apiFetch` на 401 один раз пробує refresh і повторює запит; якщо refresh теж
впав — токени чистяться, UI показує «Увійти».

## 7. Бекенд

Spring Boot 4.1 (Java 21) + PostgreSQL 18. Деталі рішень — `BACKEND_ARCHITECTURE.md`.

```
users(id UUID, google_sub UNIQUE, email, display_name, created_at, settings JSONB)
saved_words(id UUID, user_id FK, text, lemma, pos, translation, example,
            source_lang, target_lang, context, source_url, created_at, updated_at)
            UNIQUE(user_id, lemma, source_lang, target_lang)
```

| Ендпоінт | Призначення |
|---|---|
| `POST /auth/google`, `/auth/refresh` | обмін токенів |
| `GET /me`, `PUT /me/settings` | профіль і налаштування (JSONB) |
| `GET/POST/PUT/DELETE /words` | словник (POST — upsert) |
| `POST /words/sync` | дельта-синхронізація (last-write-wins) |

**Схему веде Flyway**, Hibernate лише звіряє (`ddl-auto=validate`). Застосовані
міграції ніколи не редагуються — зміни лише новим файлом `V{n}`.

**UUID як PK** (не BIGSERIAL): клієнт може згенерувати `id` офлайн ще до синку.

## 8. Збірка

`build.mjs` бандлить кожну точку входу окремо (контексти Chrome ізольовані й не
можуть ділити рантайм) і копіює статику. **`dist/` лишається пласким**, тому
переїзд джерел по папках не зачіпає `manifest.json`.

Тести (`tests/run.js`) — звичайний Node-скрипт без залежностей; він `require`-ить
CJS-бандли з `dist/test/`, які збираються окремим проходом esbuild.

Репозиторій напряму як unpacked-розширення **не вантажиться** — спочатку
`npm run build`, потім вантажити `dist/`.

## 9. Що переглянути, коли виросте

| Тригер | Дія |
|---|---|
| З'явиться веб-дашборд | Додати CORS на бекенді (зараз не потрібен) |
| Кілька користувачів | Шифрувати `settings.apiKey` at-rest |
| Словник > ~1000 слів | Пагінація `/words`; зараз popup тягне все |
| Синк видалень між пристроями | Tombstones (`deleted_at`) — свідомо поза MVP |
| Кеш перекладів на сервері | Redis (зараз навмисно немає) |
| Access-токен як refresh | Додати claim `type` і перевіряти його в `/auth/refresh` |

## 10. Відомі компроміси

- **`/auth/refresh` не розрізняє тип токена** — вкраденим access-токеном можна
  продовжувати доступ. Частково знецінює короткий TTL. Фікс — claim `type`.
- **Помилки бекенду віддають 500 замість 401/400** — немає глобального
  `@ExceptionHandler`.
- **Синк не переносить видалення** — лише додавання/оновлення (див. вище).
- **Статистика рахується на клієнті** зі списку `/words` — не масштабується
  на великий словник, але не потребує змін бекенду.
